# Аудит надёжности платформы раздачи подарков

Дата: 2026-11-27. Проверено: `index.html`, `db/schema.sql`, `db/seed_gifts.sql`, живая база Supabase `vvdegrbjngcgxffqykvj` (`newyear-gift-raffle`, eu-central-1, Postgres 17.12, статус `ACTIVE_HEALTHY`, миграция `init_event_schema` применена, подарков 118, людей 0, выдач 0 — расхождений данных пока нет, все проблемы ниже — латентные).

## Краткий вердикт

Архитектура для одноразового мероприятия выбрана правильно: отдельный проект Supabase, один источник правды в Postgres, атомарная выдача через `assign_gift` с блокировками строк. В спокойном режиме «один волонтёр, хороший Wi-Fi, список < 1000 человек» платформа будет работать.

Но надёжность «под нагрузкой мероприятия» (несколько волонтёров, плохой интернет, спешка, ошибки) — **средняя, 5/10**. Главная проблема: бизнес-правила «один человек — один подарок» защищены только в одной функции, а рядом лежит открытая дверь — прямой доступ anon-ключа на запись во все таблицы. Плюс несколько багов, которые гарантированно сработают на реальном импорте и восстановлении из бэкапа.

| Ось | Оценка | Комментарий |
|---|---|---|
| Целостность данных при выдаче | 7/10 | `assign_gift` корректен, но обходится прямым доступом |
| Защита от двойной выдачи | 5/10 | Нет UNIQUE-ограничений на уровне БД |
| Офлайн / плохой Wi-Fi | 2/10 | Нет кэша, очереди и офлайн-режима |

| Наблюдаемость / тесты | 2/10 | Только `console.error`, тестов нет |
| Простота / UX | 8/10 | Интерфейс понятный, realtime + поллинг — хорошие идеи |

## Что уже сделано хорошо (сохранить)

1. **`assign_gift` атомарен**: `SELECT ... FOR UPDATE` на человеке + `FOR UPDATE SKIP LOCKED` на подарке + проверка `received` внутри транзакции. Два волонтёра не выдадут один подарок дважды и не выдадут одному человеку два подарка *через эту функцию*. Это самое ценное место в проекте.
2. **Изолированный проект Supabase** — не трогает основную платформу, можно удалить после мероприятия.
3. **Realtime + поллинг раз в 60 сек** как страховка — правильная идея (реализация ниже с оговорками).
4. **FK `ON DELETE RESTRICT`** на `handouts`, частичный UNIQUE-индекс на `member_number`, индексы по именам/статусам.
5. **Экранирование `esc()`** в рендере — XSS через ФИО/названия подарков в целом закрыт.
6. **Ручные экспорты** JSON/CSV и поле `operator` в логе — минимум для разбора споров.

## P0 — критично, исправить до мероприятия

### P0-1. Anon-ключ может всё: обход `assign_gift` прямым доступом

**Где:** `db/schema.sql` — политики `FOR ALL TO anon USING (true) WITH CHECK (true)` + `GRANT SELECT, INSERT, UPDATE, DELETE ... TO anon` на все три таблицы. Anon-ключ лежит открытым в `index.html`.

**Почему это ломает надёжность:** любой, кто открыл `index.html` (или просто скопировал ключ), может напрямую:
- `INSERT INTO handouts` — выдать второй подарок тому же человеку в обход проверки;
- `UPDATE people SET received=false` / `UPDATE gifts SET status='available'` — «воскресить» выданные подарки и людей;
- `DELETE FROM people/gifts/handouts` — стереть всё;
- `SELECT` — скачать весь список ФИО+телефонов (приватность, см. P1-5).

То есть гарантия «ровно один раз» держится только на честности интерфейса, а не на БД.

**Как исправить (вариант А — минимум, без логина):**
Запретить прямую запись в `handouts` и в служебные поля, оставить запись только через функции `SECURITY DEFINER`:

```sql
-- функции выполняются от имени владельца, RLS не мешает им
ALTER FUNCTION public.assign_gift(bigint, text, text) SECURITY DEFINER SET search_path = public;
ALTER FUNCTION public.unassign_handout(bigint) SECURITY DEFINER SET search_path = public;

REVOKE INSERT, UPDATE, DELETE ON public.handouts FROM anon;
REVOKE UPDATE ON public.people FROM anon;  -- оставить только phone/comment через отдельную функцию или триггер
REVOKE UPDATE ON public.gifts FROM anon;

DROP POLICY anon_all_people ON public.people;
CREATE POLICY anon_select_people ON public.people FOR SELECT TO anon USING (true);
CREATE POLICY anon_insert_people ON public.people FOR INSERT TO anon WITH CHECK (true);
CREATE POLICY anon_update_contact ON public.people FOR UPDATE TO anon
  USING (true) WITH CHECK (true); -- лучше: триггер, запрещающий менять received/received_at напрямую

DROP POLICY anon_all_gifts ON public.gifts;
CREATE POLICY anon_select_gifts ON public.gifts FOR SELECT TO anon USING (true);
CREATE POLICY anon_insert_gifts ON public.gifts FOR INSERT TO anon WITH CHECK (true);

DROP POLICY anon_all_handouts ON public.handouts;
CREATE POLICY anon_select_handouts ON public.handouts FOR SELECT TO anon USING (true);
-- INSERT/UPDATE/DELETE на handouts — только из SECURITY DEFINER функций
```

И добавить триггер-стража, чтобы даже `SECURITY DEFINER`-путь нельзя было использовать для рассинхрона (см. P0-2).

**Вариант Б (правильно):** включить Supabase Auth, волонтёры логинятся, политики — по роли `authenticated`, anon — только `SELECT` или вообще ничего. Для одноразового мероприятия вариант А достаточен, если мероприятие короткое и ключ не светился в чатах.

### P0-2. Нет UNIQUE-ограничений: «один человек — один подарок» не enforced в БД

**Где:** `db/schema.sql` — в `handouts` нет `UNIQUE(person_id)` и `UNIQUE(gift_id)`.

**Сценарий:** прямой INSERT (см. P0-1), гонка при импорте дублей (P0-5), кривой restore (P0-4) — и в БД два `handouts` на одного человека. Интерфейс покажет только первый (`find`), второй станет невидимым мусором, а подарок физически уже отдан.

**Как исправить:**

```sql
CREATE UNIQUE INDEX IF NOT EXISTS handouts_one_per_person ON public.handouts (person_id);
CREATE UNIQUE INDEX IF NOT EXISTS handouts_one_per_gift   ON public.handouts (gift_id);
```

После этого даже обходной INSERT упадёт с ошибкой уникальности — это последний рубеж. Перед применением проверить, что дублей нет (сейчас их нет — база пустая).

### P0-3. Три таблицы могут расходиться: `received` / `status` / `handouts` не связаны

**Где:** `people.received`, `gifts.status/given_to` дублируют факт выдачи из `handouts`, но ни CHECK, ни триггер их не связывает.

**Сценарии рассинхрона:** ручной UPDATE, баг в коде, частичный restore. Итог: человек помечен `received=true`, а записи в `handouts` нет (в интерфейсе — «получил», но что именно — неизвестно); или подарок `given`, а `handouts` нет (подарок потерян навсегда, выдать его нельзя).

**Как исправить (два уровня):**
1. Быстрый: триггер, пересчитывающий `received`/`status` из `handouts` при каждом изменении `handouts`, или запрещающий прямое изменение этих полей вне функций.
2. Правильный: вообще убрать дублирование — `received` и `status` сделать вычисляемыми (VIEW поверх `handouts`), хранить только `handouts`. Для мероприятия достаточно уровня 1.

Диагностический запрос (полезен перед мероприятием и после):

```sql
SELECT
  (SELECT count(*) FROM people p WHERE p.received AND NOT EXISTS (SELECT 1 FROM handouts h WHERE h.person_id=p.id)) AS received_without_handout,
  (SELECT count(*) FROM handouts h JOIN people p ON p.id=h.person_id WHERE NOT p.received) AS handout_without_received,
  (SELECT count(*) FROM gifts g WHERE g.status='given' AND NOT EXISTS (SELECT 1 FROM handouts h WHERE h.gift_id=g.id)) AS given_without_handout,
  (SELECT count(*) FROM gifts g WHERE g.status='available' AND EXISTS (SELECT 1 FROM handouts h WHERE h.gift_id=g.id)) AS available_with_handout;
-- все четыре числа должны быть 0
```

### P0-4. Восстановление из бэкапа не работает и опасно

**Где:** `index.html` → `importBackup()`:

```js
if (data.people) await sb.from('people').insert(data.people.map(({id,...r})=>r));
if (data.gifts)  await sb.from('gifts').insert(data.gifts.map(({id,...r})=>r));
if (data.handouts) await sb.from('handouts').insert(data.handouts.map(({id,...r})=>r));
```

Проблемы:
- `id` отбрасываются, но `handouts.person_id/gift_id` остаются **старыми** — после вставки они указывают на чужие/несуществующие строки (FK-ошибка или привязка к не тем людям). Restore молча портит данные.
- Люди и подарки **дублируются** (нет очистки и нет дедупликации), а `member_number` UNIQUE — вставка упадёт целиком на первом конфликте.
- Три отдельные вставки без транзакции: может восстановиться половина.
- Нет `confirm()` — один клик, и база замусорена дублями.

**Как исправить:** либо честно сделать restore через RPC с отображением старых ID → новые (в одной транзакции, с очисткой или `ON CONFLICT`), либо — для одноразового мероприятия — **убрать кнопку восстановления** и оставить только экспорт + инструкцию «восстановление = `pg_dump`/`supabase db dump` из SQL Editor». Половинчатый restore хуже, чем его отсутствие.

### P0-5. Парсер импорта ломает заявленный формат «номер; ФИО; телефон»

**Где:** `index.html` → `parsePeopleText()`:

```js
let full_name = parts[0], phone = null, member = null;
for (const p of parts.slice(1)) { ... }
```

Для строки `002; Сидоров Алексей; +7922...` получается `parts[0]="002"`, `full_name="002"`, а ФИО из `slice(1)` отбрасывается (ветка `else if (!full_name ...)` никогда не срабатывает, т.к. `full_name` уже занят номером). В список попадёт человек с именем «002». Тот же дефект в CSV-парсере: имя всегда `r[0]`, заголовки просто пропускаются без сопоставления колонок (в Excel-парсере сопоставление есть — поведение несогласовано).

**Как исправить:** сначала классифицировать все части, а ФИО выбирать как первую часть, не похожую на телефон/номер:

```js
function parsePeopleText(text){
  const out = [];
  for (let line of text.split(/\r?\n/)){
    line = line.trim(); if (!line) continue;
    const parts = line.split(/\t|;|,|\s{2,}/).map(s=>s.trim()).filter(Boolean);
    let full_name = null, phone = null, member = null;
    for (const p of parts){
      if (/^\+?\d[\d\s\-()]{5,}$/.test(p) && !phone) phone = p;
      else if (/^\d{1,6}$/.test(p) && !member) member = p;
      else if (!full_name) full_name = p;
    }
    if (full_name) out.push({ full_name: full_name.replace(/\s+/g,' '), phone, member_number: member });
  }
  return out;
}
```

Плюс нормализация (схлопывание пробелов) и проверка на предпросмотре: показать, сколько строк дало пустое ФИО.

### P0-6. `loadAll()` не видит ошибки Supabase — индикатор «онлайн» врёт

**Где:** `index.html` → `loadAll()`:

```js
const [p,g,h] = await Promise.all([...]);
people = p.data||[]; ...
setConn(true);
```

Клиент Supabase **не бросает исключение** при ошибке запроса — он возвращает `{ data, error }`. `try/catch` здесь мёртв, `setConn(true)` выполняется всегда, а при обрыве сети/RLS-ошибке списки молча становятся пустыми (или частичными) при зелёной точке «все устройства синхронизированы».

**Как исправить:**

```js
const [p,g,h] = await Promise.all([...]);
const err = p.error || g.error || h.error;
if (err) throw err;
people = p.data||[]; gifts = g.data||[]; handouts = h.data||[];
setConn(true);
```

И в `catch` — не затирать старые данные пустыми (сейчас `render()` всё равно вызывается и показывает нули).

## P1 — серьёзно, сработает на мероприятии

### P1-1. Нет офлайн-режима: плохой Wi-Fi = стоп раздачи

Нет кэша (`localStorage`/IndexedDB), нет очереди повторной отправки, нет Service Worker. После перезагрузки без сети — пустой экран. Волонтёр, физически выдавший подарок при обрыве сети, не сможет зафиксировать выдачу и будет вынужден либо ждать, либо вести бумажный список (который потом никто не сведёт).

**Исправление:** кэшировать последний `loadAll` в `localStorage`, при офлайне показывать кэш с явным баннером «офлайн, данные на N минут назад», выдачу ставить в очередь `pending` и отправлять при появлении сети (с обработкой `already_received` при повторе). Минимум — PWA-манифест + Service Worker, чтобы `index.html` открывался без сети.

### P1-2. Лимит 1000 строк Supabase: тихая обрезка списков

`select('*')` без пагинации возвращает максимум 1000 строк по умолчанию. При >1000 людей/подарков/выдач интерфейс покажет неполные данные без предупреждения: человек «не найден», подарок «нет в наличии», хотя они есть. Для текущего масштаба (118 подарков) не критично, но запас прочности нулевой.

**Исправление:** цикл с `.range(from, to)` до пустой страницы или серверная функция, возвращающая всё одним запросом.

### P1-3. Realtime без дебаунса и без обработки статусов

Каждое `postgres_changes`-событие дёргает полный `loadAll` (3 запроса). Массовый импорт из 500 строк = сотни перезагрузок, гонки ответов (поздний ответ перезапишет свежий). Статус канала (`SUBSCRIBED`/`CHANNEL_ERROR`/`TIMED_OUT`) не обрабатывается — зелёная точка не отражает realtime. Канал с `Math.random()` никогда не отписывается.

**Исправление:** дебаунс 300–500 мс, обработка `subscribe(status => ...)` с переподключением и честным индикатором, один стабильный `channel('sync')`.

### P1-4. Дубли людей: проверка «в JS, потом INSERT» + нет нормализации

`doImport`/`importFile` сверяют с локальным кэшем и потом вставляют пачкой. Два волонтёра одновременно, двойной клик, «Иванов  Иван» vs «Иванов Иван», «ё» vs «е» — и дубль создан. Один и тот же человек под двумя `id` сможет получить два подарка легально. `addPerson` вообще без проверки дублей. Конфликт по `member_number` роняет **весь** батч импорта.

**Исправление:** UNIQUE-индекс на нормализованное имя (`lower(regexp_replace(trim(full_name), '\s+', ' ', 'g'))`) или обязательный `member_number` + `ON CONFLICT DO NOTHING` с отчётом «пропущено N дублей». Вставку делать порциями с подсчётом успехов/пропусков, а не одним запросом «всё или ничего».

### P1-5. Приватность: список ФИО+телефонов открыт миру

Anon-ключ публичен, `SELECT` разрешён всем. Любой в интернете может выгрузить персональные данные участников (152-ФЗ / GDPR). Для профсоюзного мероприятия это реальный риск, а не теория.

**Исправление:** минимум — предупредить в README, ограничить время жизни проекта, удалить проект сразу после мероприятия (уже предусмотрено), не светить ключ в публичных репозиториях. Правильно — Auth + роли (см. P0-1 вариант Б) и убрать телефоны из `SELECT` для anon, если они не нужны на раздаче.

### P1-6. `unassign_handout` без блокировок и с удалением истории

Функция делает `SELECT` без `FOR UPDATE`, безусловно возвращает подарок в `available` и `DELETE` из `handouts`. Два параллельных undo одного и того же — оба «успешны». История стирается: после отмены нельзя доказать, что выдача была. Нет проверки, что подарок всё ещё `given` именно этому человеку.

**Исправление:**

```sql
SELECT person_id, gift_id INTO ... FROM handouts WHERE id = p_handout_id FOR UPDATE;
-- проверить gifts.status='given' AND given_to=v_person_id, иначе вернуть ошибку
-- вместо DELETE — soft-delete: cancelled_at/cancelled_by, или перенос в audit-таблицу
```

**Применено (в текущей версии):** `unassign_handout(bigint, text)` с `FOR UPDATE` на `handouts`/`gifts`/`people`, проверкой состояния и параметром `p_operator`. История не теряется: таблица `handouts_history` хранит **отдельные записи событий** — `assign_gift` пишет событие `give` (время выдачи, кто выдал), `unassign_handout` пишет отдельную запись события `cancel` (своё время, кто отменил). Обе записи связаны по `id` (id выдачи из `handouts`), поэтому в логе выдача и отмена видны как связанная пара со своими временами. Читать историю anon может только через `SECURITY DEFINER`-функцию `get_handout_log` (для экрана «Лог»).

### P1-7. Двойной тап по «Выдать»

Кнопка не блокируется на время RPC. Двойной тап = два `assign_gift`. БД спасёт (второй получит `already_received`), но пользователь увидит два тоста и закроет модалку — путаница в очереди.

**Исправление:** флаг `inFlight`, `btn.disabled=true` до ответа, идемпотентность по `person_id`.

### P1-8. Нет автоматических бэкапов; free-tier может уснуть

Единственный бэкап — ручной JSON по кнопке, про которую забудут. Бесплатный проект Supabase ставится на паузу при неактивности и не имеет PITR. Пауза посреди мероприятия = полная остановка.

**Исправление:** перед мероприятием — `pg_dump` / снапшот, на мероприятии — напоминание/автоэкспорт каждые N выдач, держать проект «тёплым» (периодический запрос), рассмотреть Pro на один месяц ради PITR и отсутствия пауз.

## P2 — мелочи и шероховатости (исправлять по остаточному принципу)

1. **Двойное экранирование** в `renderRazdacha`: `sub` уже содержит `esc(h.gift_name)`, потом ещё раз `esc(sub)` — в интерфейсе появятся `&amp;` и т.п.
2. **Поиск с прыжком фокуса:** каждый ввод перерендеривает весь список и дёргает `focus()` — на мобильных курсор прыгает в конец, клавиатура может закрываться. Лучше рендерить только список, не трогая инпут.
3. **CSV-экспорт без экранирования и без BOM:** `;` и переносы в ФИО ломают файл, кириллица в Excel — кракозябры. Добавить `\ufeff` и кавычки.
4. **CSV-импорт игнорирует заголовки** (см. P0-5) — сопоставить колонки как в Excel-ветке.
5. **`addGift` без верхней границы:** можно ввести 1 000 000 и повесить БД одним INSERT. Ограничить, напр., 500 за раз.
6. **Название подарка:** в UI типы группируются по точному `name`, в БД `assign_gift` сравнивает `lower(name)` — «Кружка» и «кружка» посчитаются по-разному в интерфейсе и одинаково в БД. Нормализовать при вставке.
7. **`importBackup` без `confirm()`** (см. P0-4) и `clearPeople` без повторного ввода — опасные действия рядом с обычными кнопками.
8. **`user-scalable=no, maximum-scale=1.0`** — ломает зум для слабовидящих. Убрать.
